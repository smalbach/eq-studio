Un 200 no es un test que pasa.

Endpoint Quality verifica cualquier API HTTP contra su contrato OpenAPI: status, schema, autenticación 401/403, persistencia real de lo que se escribe y flujos encadenados. Y la somete a carga, estrés, pico y resistencia.

Lo que un test de humo no ve

Cada respuesta se valida contra el schema que el propio contrato declara. Cada escritura se vuelve a leer. Cada operación protegida recibe sus casos 401 y 403.

Verificación funcional

Status y schema por operación, escrituras que se releen para comprobar que persistieron y flujos encadenados que limpian lo que crean.

Autenticación real

Casos 401 y 403 automáticos. Bearer, API key, basic, OAuth2, cookies, firma HMAC y mTLS, todo cifrado y nunca devuelto.

Carga, estrés, pico y resistencia

El mismo proyecto sirve para pruebas de rendimiento, con presupuestos de latencia por operación que nunca se inventan.

Casos negativos

De cada schema de entrada salen casos con una sola falta: campo ausente, tipo equivocado, fuera de rango, enum o formato.

Cualquier contrato

OpenAPI 3.0 y 3.1, Swagger 2.0 y colecciones de Postman. Entre dos versiones ves qué cambió y qué rompe clientes.

Local, CI y nube

Informes HTML, SARIF y JUnit, programaciones con avisos por Slack, webhook o email, y sincronización entre equipos.

Así se ejecuta cada test

Sin escribir tests a mano. Sigue una operación, PATCH /products/{id}, desde el contrato hasta el informe. El orden corre las lecturas primero y los DELETE al final, para que un borrado roto no contagie de rojo al resto.

1 · Lee el contrato

El contrato ya dice qué debe responder cada operación: status, schema, seguridad y qué entra.

/products/{id}:  patch:    security: [ bearer ]    requestBody: ProductPatch    responses:      200: Product   # price: number      401, 403, 422

2 · Genera los casos

De esa sola operación salen ocho casos. Cada negativo rompe una sola regla del schema de entrada.

200 schema de Product 401 sin token 403 token de solo lectura 422 falta name 422 price: "abc" 422 price: -1 GET relectura p95 ≤ 300 ms

De las 24 operaciones del contrato salen 186 casos.

3 · Envía la petición

Contra el entorno que elegiste, con la credencial que pide cada caso.

eqstaging.api
PATCH /products/42 HTTP/1.1Authorization: Bearer ••••••••Content-Type: application/json { "price": 19.9 }

4 · Valida la respuesta

Un 200 no basta: cada campo se compara con el schema que el contrato declara.

  • ✓status 200esperado 200
  • ✓id: 42integer
  • ✓name: "Lámpara"string
  • ✗price: "19.90"string ≠ number
  • ✓38 mspresupuesto 300 ms

5 · Relee y limpia

Lo que se escribe se vuelve a leer para probar que persistió, y lo que se crea se borra al final.

  • ✓GET /products/42coincide con lo escrito
  • ✓DELETE /products/42204 limpiado
  • ✓GET /products/42404 ya no existe

El fallo queda en report.html, SARIF y JUnit, con la petición y la respuesta exactas.

También en la terminal y en tu CI

          
La CLI eq corre los mismos proyectos sin servidor. Sale con 0 si todo pasó y 1 si algún caso falló, y escribe JUnit, HTML y SARIF.

        

        

          
sin instalar nada


# la app y el API en http://127.0.0.1:4400
npx endpoint-quality serve --open

# en CI: falla el job si el contrato no se cumple
npx endpoint-quality run --file proyecto.eq.json \
  --env staging --base-url "$URL" --token "$TOKEN" \
  --junit eq-report.xml --sarif eq.sarif

# ¿el contrato nuevo rompe clientes?
eq diff viejo.yaml nuevo.yaml
